# Принятые решения проекта

Короткий документ: почему проект выглядит именно так. Читай до проектирования, чтобы не предлагать переделки без причины.

## Modular monolith, без микросервисов

FastAPI + Next.js в одном репозитории, PostgreSQL общий. Границы модулей проведены по домену (`learning`, `assessment`, `skill_graph`, `curriculum`, `mentor`), но не enforced типами сервисов. Причина: MVP с одним разработчиком; разделение появится, когда появится независимая нагрузка, а не заранее.

## Evidence — единственный источник mastery

`UserSkill` — проекция, а не истина. Истина — append-only журнал `SkillEvidence` плюс аудит `SkillMasteryAudit`. Любое изменение mastery должно объясняться конкретной записью evidence. Причина: иначе невозможно объяснить пользователю, почему его уровень изменился.

## Assisted и independent разделены всегда

`assisted` и `hint_count` — обязательные поля evidence. Полное решение с подсказкой не доказывает самостоятельность. Причина: центральная гипотеза продукта — наставник учит, а не делает работу за ученика.

## Runner fail-closed

`runner.py` бросает `RunnerUnavailable` и никогда не исполняет код в процессе API. Попытка сохраняется со статусом `unavailable`, это не успех. Причина: исполнение пользовательского кода без изоляции — дыра, которую нельзя закрыть ретроспективно. Флаг включения намеренно отсутствует.

## Один вызов AI Gateway, без vendor-логики в домене

Домен знает только про `ai_gateway` и схемы ответов. Конкретный провайдер, модель и ключи — конфигурация. Structured outputs валидируются Pydantic до использования. Причина: смена провайдера не должна быть миграцией бизнес-логики.

## Клиент не решает, что он знает

Клиент не передаёт user ID, оценку, статус завершения или ключ ответа. Всё определяется сервером по сессии, CSRF обязателен на изменяющих запросах. Причина: иначе прогресс и mastery можно подделать из браузера.

## Контент версионируется

Изменение смысла урока или ответа требует новой версии, а не правки на месте. Причина: иначе прошлый evidence перестаёт соответствовать тому, что ученик видел.

## Модели выбираются по качеству/цене

Массовые роли на дешёвых моделях, премиум — где вызовов единицы и цена ошибки высока. Распределение и коэффициенты в `model-routing.example.json`. Причина: агент, который стоит в 6 раз дороже при том же качестве, снижает число вызовов, а не повышает качество.

## Редактор кода — CodeMirror 6, а не Monaco

Поле кода на странице урока — `apps/web/app/learning/code-editor.tsx` на ядре CodeMirror 6
(`@codemirror/state`, `view`, `commands`, `language`, `autocomplete`, `lang-python`).
Обёртка `@uiw/react-codemirror` и её `basicSetup` намеренно не используются: они тянут
поиск, lint и UI автодополнения, которые странице урока не нужны.

Компонент грузится через `dynamic(..., { ssr: false })`, поэтому не входит в First Load JS
страницы: `/learning` остаётся около 112 kB, тогда как статический импорт давал 249 kB.
Monaco отклонён по трём причинам: `monaco-editor` распакован на ~97 MB и тянет worker-пути,
несовместимые с Next 15 App Router без webpack-трюков; редактор нужен только на одной
странице и только для Python; визуальный язык проекта задаётся вручную и не должен
зависеть от темы Monaco.

Причина выбора: Monaco — полноценная IDE-среда, а задача здесь — одно поле ввода с
подсветкой Python и автоотступом, где лишний вес и SSR-риск не окупаются.

## Страница урока разбита по домену, состояние живёт в page.tsx

`app/learning/page.tsx` только загружает данные и связывает состояние с
`LessonTheory`, `LessonPractice`, `KnowledgeCheckSection`, `AttemptHistory` и
`CoursePathSummary`. Полный интерактивный маршрут остаётся в `course-path.tsx` и не
дублируется. Причина: страница была самым перегруженным местом фронтенда, а смешивание
загрузки и разметки делало невозможным проверять части по отдельности.

## Упражнение показывает честное состояние Runner

Форма упражнения сохраняет попытку и прямо говорит, что код не выполнялся. Проценты
mastery не показываются как факт уровня: mastery — оценка модели, а результат проверки
знаний отображается счётом «верных ответов N из M». Причина: см. «Evidence — единственный
источник mastery» и правило UI: mastery — не истина, а модель.

## Knowledge Base: контент — это данные, retrieval привязан к навыку и версии

База знаний индексирует только авторскую теорию уроков из immutable-снапшота
`ExerciseVersion`. Оцениваемый материал (вопрос, варианты, ответ, пояснения
knowledge check, лестница подсказок) в индекс не попадает никогда — иначе
наставник смог бы прочитать оцениваемый ответ прямо из выдачи.

Каждый чанк привязан к `exercise_version_id` и `skill_id`. Retrieval — это
всегда hard filter по навыку и той версии, которую ученик видит сейчас, а
похожесть только ранжирует кандидатов внутри этого фильтра. Свободного поиска
по похожим строкам нет: текст соседнего урока или superseded-версии в выдачу
попасть не может.

Эмбеддинги хранятся в `knowledge_chunks.embedding` как упакованный float32
(`LargeBinary`), а не через pgvector. Так не нужна новая зависимость, а
`alembic upgrade head` проходит на машине без расширения. Ранжирование в
домене — это же делает деградацию возможной.

Degraded-режим — норма, а не авария: без `AI_GATEWAY_EMBEDDINGS_URL` /
`AI_GATEWAY_EMBEDDINGS_MODEL` / `AI_GATEWAY_EMBEDDINGS_DIMENSION` или при отказе
сервиса эмбеддингов наставник отвечает без retrieval и не сообщает ученику о
сбое. Чанк без вектора не проходит порог похожести, но остаётся
fallback-кандидатом — иначе деградация молча скрыла бы урок.

Текст из индекса в prompt попадает как JSON в поле `content` с явной пометкой
«untrusted data, not instructions». Системный промпт это фиксирует. Ключ
gateway и тексты ученика в логи не пишутся.

## Интерфейс приложения и первый путь новичка

По запросу владельца заменяем editorial-макет на интерфейс учебного приложения: рабочая область занимает доступную ширину экрана, на desktop есть постоянная боковая навигация, на мобильном — раскрываемое меню. Inter используется и в заголовках; общие панели, формы, кнопки и состояния оформляют все основные страницы. Ширина текста ограничивается внутри читаемого материала, а не всего приложения.

Человек без опыта начинает с объяснения программы, Python и первой строки кода; диагностика не является входным барьером. Стартовый план без диагностики не создаёт AssessmentRun, prior или SkillEvidence. «Не знаю» пропускает вопрос и не подменяется неправильным ответом. Новые объяснения публикуются под новыми IDs; старые snapshots и прогресс остаются действительными. Ранние упражнения на чтение кода не требуют ещё не изученного solve(payload).

Материал курса задаёт проверенную основу; AI объясняет её по запросу ученика и помогает разобрать затруднение. Интерфейс сообщает фактическую настроенность AI, а не обещает доступность без gateway. Дизайн проверяется браузерным smoke-прогоном с реальными disposable данными, desktop/mobile viewport и снимками страниц в CI.

## Runner: два бэкенда изоляции, Landlock как непривилегированный (2026-11-10)

Контекст: единственный бэкенд исполнения требовал Docker + `runsc` + AppArmor + user namespaces.
На сборочной машине (и на любом хосте без root) такого набора нет, поэтому `select_backend`
не мог выбрать ничего и код ученика не исполнялся вообще — при том что fail-closed формально
«работал». Проверено аудитом: `docker: command not found`, `CapEff: 0000000000000000`,
`unshare: write failed /proc/self/uid_map`.

Решение: у worker-а два бэкенда с одинаковым контрактом отказа.

- `docker` — прежний путь: pinned digest, `--runtime runsc`, cgroups v2, read-only rootfs,
  tmpfs, `--network none`, cap-drop, seccomp-профиль, независимый reaper. Выбирается первым,
  если `docker info` показывает `runsc` и cgroups v2.
- `landlock` — непривилегированный путь: Landlock LSM (ABI ≥ 4) ограничивает файловую систему
  allow-list-ом, TCP bind/connect и (ABI ≥ 6) сигналы и abstract unix sockets; seccomp-BPF
  запрещает fork/clone/clone3/execve/socket/connect/mount/ptrace/io_uring/keyctl/bpf/memfd и
  смену uid; rlimits задают CPU, address space, размер файла и число дескрипторов; процесс
  живёт в собственной сессии, убивается группой, а остатки ищутся по маркеру `SANDBOX_JOB`
  в `/proc/*/environ` и добиваются независимым reaper-ом.

Выбор: `RUNNER_SANDBOX_BACKEND=auto|docker|landlock`. `auto` = docker, если он пригоден,
иначе landlock, если ядро даёт Landlock ABI ≥ 4, иначе **отказ** `no_sandbox_backend`.
Приём задания невозможен без свежей self-attestation: worker сам прогоняет набор атак
(чтение `/home/*/.env`, запись вне job-каталога, TCP-connect, fork, exec, сигнал чужому
процессу) и требует, чтобы каждая была отклонена; при утечке — `NotReady`, а не «попробуем
без изоляции».

Альтернативы и почему отклонены: rootless Podman — требует user namespaces, а они на хосте
запрещены; `bwrap`/`nsjail` — то же ограничение; запуск в процессе API — запрещён инвариантом;
ослабить проверку и «работать без изоляции» — прямое нарушение DoD.

Следствие: на хосте с Docker обязательно проверять контейнерный путь (он остаётся
production-профилем и по умолчанию), на хосте без root продукт всё равно исполняет код и
проходит 90 заданий. Ограничение Landlock-пути: нет отдельной сети/UID-неймспейса и cgroup,
поэтому лимиты держатся rlimit-ами и родительским таймером, а не cgroups; это записано в
`docs/RUNBOOK.md` и проверяется тестами `apps/runner/tests/test_landlock_sandbox.py`.

## Каталог заданий — артефакт деплоя, а не web-ассет (2026-11-10)

Hidden expected values живут только в каталоге runner-хоста. Для локальной проверки и тестов
каталог и PKI генерируются `scripts/runner-dev-bootstrap.py` в `.runner-dev/` (каталог в
`.gitignore`, права 0700/0600, срок сертификатов 2 дня). Скрипт не заменяет reviewed attestation
в production: там attestation подписывает оператор.

## Прогресс, план дня и продолжение работы

Страницы «Мой прогресс» и «Повторения» доступны из общей навигации. Dashboard получает следующий доступный урок и назначенные повторения через `/learning/today`. Это чтение текущих рекомендаций: просмотр не создаёт учебную сессию, evidence или completion. Оценка длительности не считается фактически потраченным временем.

`/learning/progress` строит историю и агрегаты из записанных источников пользователя. Учебные наблюдения при изучении, самостоятельные/с подсказками и наблюдения при повторении разделены. Неизвестные модельные оценки возвращаются как `null`; retention показывается только после реального повторения. Событие без evidence остаётся активностью, но не добавляет освоения. Дни группируются по текущему смещению часового пояса устройства; это фиксированное смещение для выбранного периода, без пересчёта исторических переходов на летнее время.

Просмотр сохранённого кода попытки и материала проекта требует владельца. GET не публикует контент, не выполняет код и не меняет evidence. Источники не входят в публичное портфолио. В редактор кода можно восстановить только подтверждённую точную версию текущего упражнения и совпадающий формат. Замена сохраняет предыдущий черновик; при недоступном сохранении замена не производится. Browser drafts привязаны к пользователю и версии (для проектов — этапу), очищаются при выходе/удалении аккаунта. Шаг урока и неотправленные варианты ответа восстанавливаются локально, без восстановления клиентской «правильности» или completion.

Текущая карьерная цель читается отдельно от ограниченной истории вакансий. Ссылки на уроки и необходимые основы используют общую серверную prerequisite policy и immutable publications. Последняя отправка каждого этапа проекта определяется отдельно от ограниченной истории, чтобы множество правок другого этапа не сбрасывало прогресс проекта.

## Синхронизация черновиков и сохранённые занятия

Черновики lesson flow, кода authored function exercise, объяснения и этапа проекта сохраняются сервером отдельно от отправленных результатов. Клиент передаёт public identity и ожидаемую revision; сервер проверяет владельца и exact persisted context. Незавершённые значения не проверяются на правильность и не создают evidence. Конфликт требует выбора, а очистка сохраняет tombstone revision. Перед заменой сохраняется локальный предыдущий вариант; при недоступном backup замена блокируется. Серверные черновики остаются после logout и входят в owned account export/delete.

Учебное занятие — отдельная StudySession, не изменение рекомендательного CurriculumSession. Сервер фиксирует public focus snapshot и время при явном начале; heartbeat имеет lease 60 секунд и ограничивает время после потери вкладки. Скрытая вкладка отправляет pause best effort. GET ничего не начисляет в БД и не возобновляет отсчёт. Один открытый таймер, revision CAS, явный resume и терминальные completed/abandoned отделены от учебных результатов. Время по таймеру не измеряет внимание и не меняет mastery.

## Наблюдаемость: метрики в приложении, JSON-логи, Sentry по флагу (2026-11-11)

Метрики отдаёт сам API на `/metrics` (prometheus-client), без отдельного exporter-а: меньше
движущихся частей, и нельзя забыть обновить дублирующий процесс. Лейблы — только шаблон маршрута,
метод, статус, задача и модель; идентификаторы пользователей, уроков и заданий в метрики не
попадают, иначе кардинальность растёт от действий пользователя.

Логи — одна JSON-строка на событие в stdout (`app/logging_config.py`). Сборщик (journald, Loki,
CloudWatch) забирает их без парсера. Промпты, тексты ученика и ключи не логируются: `ai_call`
содержит только task/model/attempts/tokens/micro_usd/latency.

Sentry включается только при `SENTRY_DSN` и перед отправкой чистит событие: тело запроса, query
string, `Authorization`, `Cookie`, `user`. Иначе код ученика и сессионная cookie уехали бы в
третью сторону.

Альтернативы: OpenTelemetry-коллектор (лишний компонент без трейсов), логи с парсером на стороне
сборщика (хрупко), метрики из PostgreSQL-представлений (нагрузка на БД). Отклонены.

## Очередь без Redis (2026-11-11)

Очередь исполнений durable в PostgreSQL (`execution_jobs`, `SELECT … FOR UPDATE SKIP LOCKED`),
поэтому Redis в production-стек не входит: он добавил бы вторую точку отказа и второй источник
истины без выигрыша на текущем объёме. Кэш уроков и rate limits тоже живут в БД и в памяти
процесса. Когда появится измеренная потребность (например, >100 rps на чтение программы),
Redis добавляется отдельным ADR с цифрами, а не заранее.

## Деплой проверяется структурой, а не запуском, на верстаке (2026-11-11)

На сборочной машине нет Docker и root, поэтому `docker compose up` здесь невозможен. Артефакты
(`compose.prod.yml`, Caddyfile, Prometheus-алерты, дашборд Grafana) проверяются тестами структуры
(`apps/api/tests/test_deploy_config.py`): обязательные сервисы, healthcheck, только Caddy
публикует порты, runner не получает секретов приложения, алерты и панели ссылаются на реальные
метрики. Живой прогон — на целевом хосте по `docs/RUNBOOK.md`; до него деплой считается
неподтверждённым, и это записано в `docs/STATUS.md`.

## Внешние контуры без боевых аккаунтов (2026-11-11)

Email, Telegram и платежи реализованы адаптерами и не имеют боевых провайдеров. Решение:
не выдумывать ключи и не подменять доставку заглушкой, а держать продукт честным.

- **Email.** `app/notifications.py` пишет в durable outbox; dispatcher отправляет через SMTP,
  если заданы `SMTP_HOST`/`SMTP_PORT`/`EMAIL_FROM`. Без провайдера письма не уходят, и
  регистрация с подтверждением email в production не завершается: `docs/RUNBOOK.md` требует
  SMTP до первого деплоя. Dev-токен подтверждения выдаётся только при
  `DEV_ACCOUNT_TOKENS=true` и `APP_ENV != production` — в production этого пути нет.
- **Telegram.** Бот продукта регистрируется отдельно от бота Hermes-агента (у агента свой
  токен для отчётов, использовать его как бота продукта нельзя). Webhook требует публичный
  HTTPS-домен и `TELEGRAM_WEBHOOK_SECRET`. До этого binding-эндпоинты отвечают отказом, UI
  не обещает доставку.
- **Платежи.** `BILLING_PROVIDER`-независимый адаптер с проверкой подписи вебхука.
  `GET /billing/plans` возвращает `checkout_available=false`, пока не заданы URL, ключ и
  секрет вебхука, и UI в этом случае не показывает кнопку оплаты. Мёртвой кнопки нет.

Следствие: продукт можно развернуть и учиться без платежей и Telegram, но нельзя считать
регистрацию завершённой без SMTP. Это записано в `docs/RUNBOOK.md` §1 и в `docs/STATUS.md`.

## Ошибки фронтенда: Sentry по флагу, без сборки source maps на стороне CI (2026-11-11)

`@sentry/nextjs` подключён через `instrumentation-client.ts` и `instrumentation.ts`, а не через
`withSentryConfig`: плагин на этапе сборки требует auth-токен и публикацию source maps, а без них
он молча усложняет сборку. Инициализация выполняется только при заданном DSN, поэтому `npm run dev`
и CI-сборка не обращаются к третьей стороне.

Перед отправкой события удаляются тело запроса, query string, cookie и `user`. CSP разрешает
ingest-хост только если DSN был задан **на этапе сборки**: `connect-src` собирается из
`NEXT_PUBLIC_SENTRY_DSN`. Смена DSN требует пересборки фронтенда — это осознанный компромисс:
CSP статична, а динамическая политика на каждый запрос дороже и сложнее в отладке.

Альтернативы: `withSentryConfig` (нужен токен и source map upload — лишняя связка с CI),
отдельный прокси `/monitoring` (Sentry-recommended, но добавляет маршрут и разрешает `connect-src 'self'`;
вернёмся к нему, когда появится реальный DSN и потребность обходить блокировщики).

## ADR. SMTP как основной транспорт писем (W3, 2026-11-11)

**Контекст.** Доставка писем была HTTP-адаптером к внешнему релею, а запрос сброса пароля проверял
только этот адаптер. Провайдера у проекта нет, поэтому публичная регистрация не могла подтвердить
почту, а ASVS 2.2.3 оставался открытым.

**Решение.** Транспорт — обычный SMTP (`smtplib`, STARTTLS/SSL), настройки только из окружения:
`SMTP_HOST`, `SMTP_PORT`, `SMTP_FROM`, `SMTP_USER`/`SMTP_PASSWORD`, `SMTP_TLS`. HTTP-адаптер релея
сохранён как альтернатива. Креденшелы поверх незашифрованного канала запрещены: при
`SMTP_TLS=none` и заданном пользователе конфигурация считается невалидной и канал остаётся выключенным.
Если SMTP не настроен, `email_available()` = false, кабинет честно показывает «канал не подключён»,
а запрос сброса всё равно отвечает 202, чтобы не раскрывать состояние аккаунта.

Письмо о неудачных входах отправляется при неудачном входе в существующий аккаунт, не чаще раза в час
(idempotency-key по часу), только на подтверждённый адрес. Неизвестный адрес писем не получает и
ответ не отличается.

**Следствие.** Боевая доставка требует только четырёх переменных от владельца; проверка идёт против
реального SMTP-сокета в CI (`apps/api/tests/test_email_delivery.py`, 7 тестов, локальный SMTP-сервер
на loopback), без внешнего провайдера.

**Найденный по пути дефект.** `request_password_reset` проверял только `email_configuration()`,
поэтому при настроенном SMTP письмо сброса молча не ставилось в очередь, а API возвращал 202.
Тест на сквозной сброс пароля поймал это до релиза.

## ADR. Telegram — полноценный канал обучения (W4, 2026-11-11)

**Контекст.** До этого был только адаптер доставки: привязки не было, команд не было, тестов не было.
По спеке бот несёт ежедневный план, быстрый квиз, streak и недельный отчёт — это отдельный канал
обучения, а не лента уведомлений.

**Решение.**
* Привязка — одноразовым кодом из кабинета (`/me/telegram/bind-token`, 15 минут, deep-link
  `t.me/<bot>?start=<code>`). Код гасится в момент привязки, второй чат им воспользоваться не может.
* Отвязка сохраняет строку истории: `revoked_at` заполняется, `chat_id` получает префикс `revoked-`,
  чтобы номер освободился для другой привязки, а очередь сообщений этого чата отменяется.
* Вебхук: секрет в пути **и** в заголовке `X-Telegram-Bot-Api-Secret-Token` (сравнение
  `hmac.compare_digest`), лимит тела 128 КБ, каждый `update_id` записывается в `telegram_updates`
  и повторная доставка не повторяет действие, неизвестные типы update получают 400.
  Без токена и секрета вебхук отвечает 503, кабинет честно показывает «канал не подключён».
* Команды: `/start`, `/link`, `/unlink`, `/today`, `/progress`, `/quiz`, `/streak`, `/settings`,
  `/quiet HH:MM-HH:MM`, `/help`.
* Квиз: один вопрос по текущей теме с inline-кнопками. Ответ пишется как настоящая
  `KnowledgeCheckAttempt` + `KnowledgeCheckResponse` и попадает в evidence с `metadata.channel=telegram`,
  поэтому он виден в прогрессе и в мастерстве, а не живёт отдельной жизнью. Подсказок в боте нет,
  поэтому `assisted=false` — это факт, а не упрощение.
* Тихие часы и выключенные уведомления не выбрасывают сообщение, а откладывают его на 30 минут.

**Следствие.** Токен живёт только в `.env` на сервере и в GitHub Secrets; в репозитории его нет.
Публичный вебхук требует боевого HTTPS-домена: на верстаке ничего не публикуется, поэтому
`setWebhook` выполняется на целевом хосте по инструкции из `docs/RUNBOOK.md`.

## ADR. OAuth-вход вне v1.0 (6.2, 53.3)

**Контекст.** Регистрация и вход работают на email и пароле с подтверждением почты, сбросом,
отзывом сессий и CSRF. OAuth требует регистрации приложения у провайдера и владения доменом
для redirect URI.

**Решение.** Вход через сторонние провайдеры не входит в v1.0. Причина внешняя: без приложения
у Google/GitHub и без домена проверить поток нельзя, а имитация «входа» без провайдера — обман.
В интерфейсе нет кнопок OAuth, обещаний и упоминаний провайдеров; единственный способ входа —
форма email и пароля.

**Что теряет пользователь.** Один лишний шаг при регистрации. Компенсация: подтверждение почты,
сброс пароля и отзыв сессий работают.

**Что нужно, чтобы включить.** Регистрация приложения у провайдера, домен для redirect URI,
`OAUTH_CLIENT_ID`/`OAUTH_CLIENT_SECRET` в `.env`. Код: одна таблица связей и один callback.

## ADR. Импорт репозиториев вне v1.0 (33.6)

**Контекст.** Спека описывает ingestion репозитория, tree-sitter, граф зависимостей и ревью
большого кода. Это отдельный продукт: он требует GitHub App, очереди индексации, хранилища
артефактов и собственного контура приватности.

**Решение.** Repository intelligence не входит в v1.0. В интерфейсе нет импорта репозитория и
связанных обещаний. Проверка кода ученика (runner) и ревью по рубрике работают с тем кодом,
который ученик вставил сам.

**Что теряет пользователь.** Автоматический разбор своего репозитория. Он получает ревью
собственных решений по шести критериям.

## ADR. Интервью-симулятор вне v1.0 (76.1)

**Контекст.** Спека описывает HR-симуляцию, live coding и адаптацию под вакансию.

**Решение.** Симулятор не входит в v1.0. Вместо него — статические гайды по собеседованию
(`/interviews`, шесть разборов: язык, данные и SQL, API, чтение кода, тесты, поведенческая часть)

оценка — от наставника, а не имитация найма.

**Что нужно, чтобы включить.** Сценарии интервью с рубриками, запись и разбор ответов, отдельный
контур приватности для аудио/текста.

## ADR. Локали: только русский в v1.0 (81.2)

**Контекст.** Спека допускает `concept_id + locale + content` для ru/en.

**Решение.** Контент и интерфейс — только ru. Переключателя языка в UI нет и не было;

## ADR. Redis: очередь и throttle на PostgreSQL достаточны (34.2)

**Контекст.** Спека предлагает Redis для queue, cache, rate limits и locks. Текущая реализация:
durable-очередь на таблице `execution_jobs` с advisory-lock на приём, throttle на таблице
попыток, кэш ответов — в БД.

**Замеры на этой конфигурации.** k6, 10 VU: p95 = 76 мс, 0 % ошибок; compose-стек в CI проходит
сценарий полностью; API-набор 447 тестов, включая конкурентные. Точка, где БД-очередь станет
узким местом, будет измерена в W5 (100–200 VU) — до этого добавлять Redis значит усложнять
развёртывание без числа, которое это оправдывает.

**Решение.** Redis не внедряется в v1.0. Порог пересмотра: если W5 покажет деградацию приёма
заданий или throttle на конкурентной нагрузке, появляется ADR с числами «до/после» и Redis
входит как отдельный сервис в compose.

**Следствие.** Меньше сервисов в деплое, меньше состояния, бэкап — только PostgreSQL.
