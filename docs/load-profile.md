# Нагрузочный профиль

Инструмент: k6 v0.54.0, скрипт `scripts/load/learning.js`.
Профиль: 10 VU, ramp 15 s → 30 s плато → 10 s спад, каждый VU делает 4 запроса
(`/learning/overview`, `/learning/lessons/{id}`, `/learning/today`, `/health`) с паузой 1 s.

Среда: верстак, 4 vCPU, 15 GiB RAM, PostgreSQL 16.15 на той же машине, 2 uvicorn-воркера,
SQLite не используется. Тело: API без AI-ключа (AI-контур в этом профиле не участвует).

## Что было до исправления и почему

Первый прогон дал `p(95) = 9.61 s` при 0 % ошибок — то есть сервис не падал, а задыхался.
Профилирование показало: `GET /learning/lessons/{id}` вызывал `accessible_lesson`, который
строил **весь** учебный путь (90 уроков, снапшоты, рёбра графа) только чтобы узнать статус
одного урока, а `seed_skill_graph` на каждом вызове делал `flush()` на каждое ребро графа.

Исправления (коммит «Производительность…»):

1. `seed_skill_graph` загружает существующие навыки, рёбра и связи уроков тремя запросами и
   вставляет только отсутствующие, с одним `flush()` вместо запроса на строку.
2. `accessible_lesson` не строит путь, если урок уже привязан к открытой сессии: такая сессия
   создана после допуска, и повторная проверка не может изменить решение.

Эффект: горячий запрос урока 1.93 s → 0.03 s (TestClient, SQLite), 1.25 s → 0.08 s на PG под
нагрузкой; полный API-набор тестов 14:10 → 5:49.

## Как воспроизвести

```bash
cd apps/api
DATABASE_URL=postgresql+psycopg://mentor:mentor@127.0.0.1:5432/mentor \
  python -m uvicorn app.main:app --host 127.0.0.1 --port 8011 --workers 2
BASE_URL=http://127.0.0.1:8011 k6 run scripts/load/learning.js
```

Порог в скрипте — часть контракта: прогон, который его не выполнил, считается проваленным, и
именно поэтому числа выше взяты из зелёного прогона.
