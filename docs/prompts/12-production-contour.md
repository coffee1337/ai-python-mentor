# Промт 12 — Наблюдаемость, бэкапы, лимиты

## Роль

Ты — оркестратор проекта AI-наставник Python Backend. Твоя работа — **декомпозиция и запуск агентов**, а не написание кода.

Прочитай `.agents/skills/task-router/SKILL.md`, `.agents/skills/backend-implementation/SKILL.md`, `.agents/skills/security-review/SKILL.md` и `.agents/skills/verification-strategy/SKILL.md`.

**Действуй сразу.** Не задавай уточняющих вопросов, не жди подтверждения и не предлагай план без действий. Первый шаг — прочитать нужные файлы, второй — запустить агентов через `spawn_agent`. Ответ без запущенных агентов считается невыполненным.

Ограничение окружения: `max_concurrent_threads_per_session = 2`. Запускай агентов волнами по 2, дожидайся результата, потом следующая волна.

## Контекст

Все промты 00–11 выполнены. Курс покрывает `python.core` и backend-фазу 1, есть редактор кода и Knowledge Base.

В P0 спецификации есть **Logging/monitoring** и **Backups**. Сейчас это выглядит так:

- `apps/api/app/main.py` содержит только `logger = logging.getLogger("mentor.startup")` и `report_gateway_status()` в lifespan;
- в `apps/api/app/mentor.py` — **ноль** обращений к логированию: AI-вызовы, ошибки gateway и отказы не видны;
- `AIUsageLedger` пишет usage от AI-вызовов, но это **не** метрики и не биллинг — это отмечено в `UNIMPLEMENTED_STAGES.md`;
- rate limit есть только в `apps/api/app/practice.py` — это словарь в памяти процесса (`_RATE`, `LIMIT = 5`, `WINDOW = 60.0`), который не переживает перезапуск, не работает при нескольких процессах и не покрывает mentor-чат или auth;
- бэкапов нет.

Принятые решения — в `docs/decisions.md`. В частности: не логировать ключи и лишние персональные данные.

## Задача

### 1. Спроектируй наблюдаемость

Дай `architect` задачу спроектировать контур. Требуется письменно ответить:

- какие события бизнеса и отказа нужно фиксировать, а какие — нет;
- что попадает в лог, а что считается персональными данными и не попадает;
- формат логов: структурированный JSON или текст, и почему;
- как логи AI-вызовов соотносятся с `AIUsageLedger`, чтобы не было двух источников правды об одном вызове;
- какие метрики отдавать: ошибки gateway, доля недоступных упражнений, отказы Runner, latency;
- как ученик отличит «наставник думает» от «сервис сломан» — это продуктовое требование, а не только техническое.

### 2. Реализуй логирование

Дай `implementer` задачу:

- настроить структурированное логирование через стандартную библиотеку, без новых зависимостей без обоснования;
- добавить корреляционный идентификатор запроса;
- зафиксировать отказы AI Gateway, недоступность Runner и ошибки оценки;
- **не логировать** ключи, исходный код ученика, тексты вакансий и содержимое чата;
- добавить `GET /health` и `GET /ready`, где `ready` честно отражает состояние БД, а не просто отвечает 200.

### 3. Сделай rate limit настоящим

Дай `architect` задачу выбрать решение для общего лимита по пользователю, покрывающего mentor-чат, practice и auth: PostgreSQL-backed или внешний. Обоснуй выбор и учти, что при нескольких процессах лимит в памяти не работает.

Затем дай `implementer` задачу реализовать выбранный вариант и миграцию, если она нужна. Требования: `429` с внятным сообщением, лимит на пользователя, не на IP; лимит mentor-чата должен учитывать стоимость вызова, иначе один ученик съедает бюджет.

### 4. Бэкапы

Дай `devops` задачу описать и реализовать процедуру бэкапа PostgreSQL: расписание, хранение, проверка восстановления. Ключевой вопрос — **проверялась ли восстановимость на самом деле**: бэкап, который не восстанавливали, не является бэкапом. Опиши процедуру восстановления так, чтобы её можно было выполнить на тестовой базе.

### 5. Проверь качество

Дай `tester` задачу тесты на поведение: логи не содержат секретов и персональных данных; `ready` отдаёт 503 при недоступной БД; rate limit возвращает 429 и сбрасывается по окну; лимит не обходится сменой IP.

Дай `security-reviewer` задачу проверить, что наблюдаемость не стала новым каналом утечки: проверь пути, по которым текст ученика или ключ могут попасть в лог.

## Ограничения

- **Не расширяй scope.** Ни биллинга для платящих, ни админки с ролями, ни Telegram-бота — это P1 и отдельные промты.
- Не добавляй сервис-мониторинг с внешними SaaS-зависимостями без обоснования.
- Не логируй ключи и лишние персональные данные.
- Не ухудшай fail-closed поведение Runner.
- Меняй схему только через Alembic, с обратимой миграцией.

## Критерий готовности

Структурированные логи без утечек, честные `/health` и `/ready`, рабочий rate limit на несколько процессов, описанная и проверенная процедура бэкапа, `pytest`, `npm run lint`, `npm run build` зелёные.

В отчёте укажи: список событий в логах, что сознательно не логируется, схема rate limit, процедура бэкапа и результат её проверки, точный вывод проверок, что осталось непроверенным.
