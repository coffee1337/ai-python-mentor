# Промт 07 — Проектирование изолированного Runner

## Роль

Ты — оркестратор проекта AI-наставник Python Backend. Твоя работа — **декомпозиция и запуск агентов**, а не написание кода.

Прочитай `.agents/skills/task-router/SKILL.md`, `.agents/skills/backend-implementation/SKILL.md` и `.agents/skills/security-review/SKILL.md`.

**Действуй сразу.** Не задавай уточняющих вопросов, не жди подтверждения и не предлагай план без действий. Первый шаг — прочитать нужные файлы, второй — запустить агентов через `spawn_agent`. Ответ без запущенных агентов считается невыполненным.

Ограничение окружения: `max_concurrent_threads_per_session = 2`. Запускай агентов волнами по 2, дожидайся результата, потом следующая волна.

## Контекст

Все промты 00–06 выполнены. Курс наполнен, PostgreSQL работает.

**Runner — главный оставшийся блокер.** Сейчас `apps/api/app/runner.py` содержит 20 строк и всегда бросает `RunnerUnavailable`. `practice.py` сохраняет попытку со статусом `unavailable`. Код ученика не исполняется никогда.

Это значит: нет объективной проверки кода, `practice_score` в mastery не получает реального вклада, половина P0-бэклога закрыта.

Спецификация (разделы 35–41) описывает границу: API → приватный worker endpoint → одноразовый sandbox на запуск. Только worker имеет доступ к container runtime; API и web не монтируют runtime socket.

На этой машине Runner **не развернуть**: нет виртуализации, Docker не работает. Но код можно и нужно написать сейчас — развёртывание позже.

## Задача

**1. Спроектируй границу.**

Дай `architect` задачу на протокол API ↔ worker. Требуется решить и явно записать:

- формат запроса: exercise ID, версия, язык, исходный код, режим;
- формат ответа: статус, пройденные тесты, всего тестов, timeout, resource violation, stdout, stderr;
- где проходит границу доверия и что именно считается недоверенным входом;
- как обеспечить идемпотентность: повторный запрос с тем же ключом не должен исполнять код дважды;
- что worker возвращает при ошибке, таймауте и недоступности.

**2. Спроектируй модель результатов.**

Дай `api-designer` задачу на persistence: сохраняется ли только результат, или нужна история попыток с детализацией по тестам. Требуется `submission_results` и связь с `CodingAttempt` и `SkillEvidence`.

Ключевой вопрос: как результат runner становится evidence. `record_evidence` уже принимает `source_type="coding_attempt"` — проверь, что путь не обходит правила assisted/independent.

**3. Спроектируй изоляцию.**

Дай `security-reviewer` задачу. Требуется письменный ответ по каждому пункту, а не общие слова:

- network off, non-root, read-only base, временная файловая система;
- CPU, memory, PID, wall-clock, disk и лимит вывода;
- allowlist образов, команд и тестов — клиент не может их задавать;
- cleanup после таймаута, отмены и падения worker;
- mTLS или эквивалентная защита endpoint, приватная сеть, ротация учётных данных worker;
- что делать, если worker недоступен — поведение должно оставаться fail-closed.

**4. Напиши код протокола, но не исполняй код.**

Дай `implementer` задачу: реализовать контракт и клиентскую сторону в API, с подключённым к `AI_GATEWAY`-подобной конфигурации через переменные окружения. Порт worker включён, но безопасно отказывает.

Требования:

- конфигурация через `.env` (`RUNNER_URL`, `RUNNER_AUTH_TOKEN`, `RUNNER_REQUEST_TIMEOUT_SECONDS`) — эти имена уже зарезервированы в `.env.example` и закомментированы;
- при отсутствии конфигурации поведение то же, что сейчас: `unavailable`, не ошибка 500;
- клиент не передаёт произвольные команды или пути;
- код ученика **не исполняется в процессе API ни при каких настройках**.

**5. Напиши тесты протокола.**

Дай `tester` задачу: тесты на контракт с mock-ответом worker, на таймаут, на недоступность, на то, что результат worker записывается как evidence с корректным `assisted`, и на то, что публичные и hidden тесты разделены.

## Ограничения

- **Никакого исполнения кода в этом промте.** Только протокол, клиент, модели и тесты. Включение worker — отдельная задача с развёртыванием на отдельном Linux-хосте.
- Не добавляй флаг, который включает исполнение без проверенного worker.
- Не поднимай безопасность на уровне «мы доверяем коду ученика» или AST-фильтра: AST-фильтр не является границей безопасности для Python.
- Не монтируй runtime socket в API или web.
- Не логируй исходный код ученика и секреты.

## Критерий готовности

Протокол описан, клиент API реализован и fail-closed по умолчанию, модель результатов готова, изоляция описана письменно по пунктам, тесты протокола зелёные, ни одна строка ученического кода не исполняется в API.

В отчёте укажи: изменённые файлы, контракт запроса и ответа, список требований изоляции, точный вывод проверок, что осталось непроверенным и что нужно для развёртывания worker.
