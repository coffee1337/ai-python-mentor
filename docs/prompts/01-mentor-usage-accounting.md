# Промт 01 — Учёт AI-расхода в mentor-чате

## Роль

Ты — оркестратор проекта AI-наставник Python Backend. Твоя работа — **декомпозиция и запуск агентов**, а не написание кода.

Прочитай `.agents/skills/task-router/SKILL.md` и `.agents/skills/backend-implementation/SKILL.md`.

**Действуй сразу.** Не задавай уточняющих вопросов, не жди подтверждения и не предлагай план без действий. Первый шаг — прочитать нужные файлы, второй — запустить агентов через `spawn_agent`. Ответ без запущенных агентов считается невыполненным.

Ограничение окружения: `max_concurrent_threads_per_session = 2`. Запускай агентов волнами по 2, дожидайся результата, потом следующая волна.

## Контекст

Промт 00 **уже выполнен**: инструкции синхронизированы с кодом, baseline записан. Не проверяй его и не спрашивай про него — работай дальше.

Проект: Next.js 15 + FastAPI + PostgreSQL в modular monolith. Принятые решения — в `docs/decisions.md`.

Проблема: `ai_curriculum.py` полноценно учитывает расход — пишет в `AIUsageLedger` токены, признак кэша, статус, модель, и ограничивает 10 вызовов в час на пользователя. В `mentor.py:104` вызывается `ai_gateway.generate(config, messages)` — обёртка возвращает только строку и **теряет usage**. Из-за этого чат наставника — единственный путь к AI, который не виден в учёте.

Что уже есть:

- `ai_gateway.generate_with_usage(config, messages, max_completion_tokens=...)` возвращает кортеж `(content, usage)`.
- `AIUsageLedger` в `apps/api/app/db/models.py` — поля `user_id`, `generation_id`, `operation`, `model_id`, `cache_hit`, `input_chars`, `output_chars`, `input_tokens`, `output_tokens`, `status`, `created_at`.
- `generation_id` ссылается на `ai_plan_generations.id` с `ON DELETE SET NULL`, то есть допускает `NULL`. Для mentor-чата это правильный вариант: запись учёта не должна зависеть от существования плана.
- В `mentor.py` **уже есть** rate limit: сумма `attempt_count` за последнюю минуту, лимит 5, отдаёт 429 с `Retry-After`. Его не нужно писать заново.

Ограничения домена: клиент не передаёт user ID; ответы не содержат ключей и внутренних деталей провайдера; секреты не логируются.

## Задача

**1. Спроектируй изменение.**

Дай `api-designer` задачу: как записывать usage для mentor-вызова так, чтобы это было согласовано с существующим `AIUsageLedger` и не требовало новой таблицы.

**2. Реализуй.**

Дай `implementer` задачу на основе схемы от `api-designer`. Ключевые требования:

- перейти с `ai_gateway.generate` на `generate_with_usage` в `mentor.py`;
- записывать `AIUsageLedger` с `operation="mentor_chat"`, `model_id` из конфигурации, `generation_id=None`;
- `input_tokens` и `output_tokens` — только если провайдер вернул целые числа, иначе `None`;
- считать `input_chars` и `output_chars` всегда, это не зависит от провайдера;
- **при ошибке gateway тоже писать запись** со `status="gateway_error"` и сохранять текст ответа наставника;
- не логировать ключ, endpoint и тело ответа провайдера;
- не ломать существующий rate limit и идемпотентность по `request_id`.

Отдельно скажи `security-reviewer` проверить: не появляется ли новая утечка через usage или логи, и остаётся ли транзакция mentor-вызова атомарной.

**3. Покрой тестами.**

Дай `tester` задачу: тест на то, что успешный вызов пишет запись в ledger; тест на то, что ошибка gateway тоже пишет запись; тест на то, что `cache_hit` корректно отражает повторный запрос с тем же `request_id`. Тесты должны падать до правки и проходить после — не зеркаль реализацию.

## Ограничения

- Docker и PostgreSQL не работают: виртуализация не включена, WSL2 недоступен. Тесты идут на SQLite через фикстуру в `tests/test_auth.py`. Не проси `docker compose` и `psql`.
- Не меняй модель `AIUsageLedger` и не добавляй миграцию без реальной необходимости. Если `api-designer` предложит расширить таблицу — потребуй обоснование.
- Не отключай и не ослабляй существующий rate limit.
- Не добавляй ретраи к провайдеру: политика проекта — один вызов без повторов.
- Учёт токенов — наблюдаемость, а не биллинг. Подписок и квот в проекте нет, не вводи их здесь.

## Критерий готовности

Каждый mentor-вызов оставляет ровно одну запись в ledger, успех и ошибка учтены, токены не выдумываются при отсутствии в ответе провайдера, ключи не логируются, rate limit не сломан, `python -m pytest -q` зелёный, `npm run lint` зелёный.

В отчёте укажи: изменённые файлы, точный вывод `pytest` и `npm run lint`, что осталось непроверенным.
